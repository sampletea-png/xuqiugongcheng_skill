# 对齐原话

本技能对齐一句原话。它会在需求工程里多次使用，也可以单独使用。原话保留。理解分成两段，都由说出原话的人确认或改正。第一段只复述原话里有的内容。某一轮复述确认之后，再询问会改写这句话含义的事项。询问前先探索，事实写下来，只有对方能拍板的才问，一次一题。两段和术语都确认之前，不写结论。

临时产物记在 `.scratch/需求工程/<需求名称>/`。路径用文本：需求名称、对齐名称。对齐的临时文件正文同时写需求 UUID、对齐 UUID、会话 UUID，三者都不放进路径。`CONTEXT.md` 仍是整个项目的持久化术语，不写这三个 UUID。

## 步骤

1. 确认临时目录 `.scratch/需求工程/<需求名称>/` 已经存在，且其中已有需求 UUID。没有需求名称时停止。
2. 本会话若还没有会话 UUID，就运行本技能目录下的 `scripts/new-uuid.ps1` 取得一个，并在本会话中一直持有。再运行一次该脚本，取得对齐 UUID 并持有它。两次都把当前仓库根目录传给脚本。对齐 UUID 不是需求 UUID，也不是会话 UUID。此后本会话未关闭的对齐，就是会话 UUID 与本会话相同、对齐 UUID 由本会话持有、且状态为正在对齐的那些。不要自行另造 UUID。
3. 从原话取出对齐名称，作为短文本。创建 `.scratch/需求工程/<需求名称>/对齐/<对齐名称>/过程.md`。写入需求 UUID、对齐 UUID、会话 UUID、对齐名称、开始时间、状态「正在对齐」，以及原话。开始时间用来区分各次对齐何时开始。同一需求下已有相同对齐名称时，改这次还没写完的对齐名称，对齐 UUID 不变。
4. 用自己的话写一轮重述，只含原话里有的内容，状态为未确认。
5. 原话和这一轮重述并排交给对方。对方确认、改正或否定。
6. 改正或否定就再追加一轮，直到某一轮被确认。
7. 某一轮重述已确认后，先探索，再询问。探索只读：仓库根目录的 `CONTEXT.md`（有 `CONTEXT-MAP.md` 时读它指向的那份）、同一需求下已有的对齐过程与结论、`.scratch/需求工程/inbox.md` 里正在处理的那一条、这句原话和已确认的重述。推得出的事实写入过程文件的「探索」。事实不向对方提问。

   一题要同时满足三条才问：只有对方能拍板；不依赖还没回答的题；换一个答案，这句话就变成另一件工作，或变成另一个主张。原话没说清、互相矛盾，或一个词有两种指称，并且第三条成立，才属于这里。今后的决定也要第三条成立才问。

   一次只问同时满足三条的一题。用「交给对方的一题」那个外形交给对方，并把同一题写入「询问」，状态为未确认。对方回答之前，不问下一题，也不进入术语。至少给出 (a)(b)(c)：推荐答案和另外两个备选。推荐是其中一项，用 ➡️ 标出。问句写成回答「是」就接受推荐。每个答案都写思考，以及为什么是这个答案。背景写这句话的哪一处没说清，或哪一个今后的决定已经挂在这句话上。为什么问写：不先定它，已确认的重述仍有另一种含义。

   对方选定一项，或给出自己的答案，就把选择记下，状态改为已确认。对方否定这一题，选择写「不成立」，状态改为已否定。已写下的答案不覆盖。被否定的题不进入结论。

   这一题有了已确认或已否定之后，再看还有没有同时满足三条的题。没有就停止。一题都没有时，「询问」写「无」。

   例如原话「我期望实现小说编辑器」。会问：小说编辑器是作者自己写一部小说，还是也包含编辑审稿。会问是因为两个答案让这句话分别指一件工作和两件工作。不问正文按章保存还是按整部保存；原话没有出现章或保存。原话里已经出现章或保存时，这一问才成立。
8. 从原话、最后一轮已确认的重述、以及状态为已确认的询问选择里，抽出可能有多种指称的词。每个词在 `过程.md` 里记下：指什么、不指什么、其他叫法、谁这样用，状态为未确认。同一种写法有两种指称时，收成两个词。已否定的询问不抽。
9. 对方逐条确认这些词。没有需要对齐的词时，跳过这一步。
10. 最后一轮重述已确认，该问的题都已是已确认或已否定，抽出的词都已确认之后，把术语写入 `CONTEXT.md`，并在同一对齐目录写 `结论.md`。然后把过程状态改为「对齐完毕」。在那之前不写这两份。

重新查看时，打开该需求下的 `对齐/` 目录。目录名是对齐名称。读每个 `过程.md` 开头的原话、开始时间和状态。

## 交给对方的一题

```markdown
❓ **Q1** - **<标题>**: <问句。回答「是」即接受推荐。>

背景：<这句话的哪一处没说清，或哪一个今后的决定已经挂在这句话上。>
为什么问：<不先定它，已确认的重述仍有另一种含义。>

探索到的事实：
- <事实。没有则写无。>

(a) <答案>
思考：<简短思考过程。>
为什么是这个答案：<为什么它可以作为这句原话的含义。>

(b) <答案>
思考：<简短思考过程。>
为什么是这个答案：<为什么它可以作为这句原话的含义。>

(c) <答案>
思考：<简短思考过程。>
为什么是这个答案：<为什么它可以作为这句原话的含义。>

➡️ (a)
```

备选多于两个时继续 (d)、(e)，每项仍写思考和为什么是这个答案。

## 过程文件

`.scratch/需求工程/<需求名称>/对齐/<对齐名称>/过程.md`

需求 UUID：<这条需求临时文件里已有的 UUID。>
会话 UUID：<本会话生成并一直持有。同一次会话里的对齐写同一个。>
对齐名称：<短文本。也是本目录名。>

状态：正在对齐

## 原话

<原样保留。>

## 重述

- 第 1 轮：<只含原话里有的内容。>
  状态：未确认

## 探索

- 事实：
  从哪里来：

## 询问

- 第 1 题：<标题>
  问句：
  背景：
  为什么问：
  探索到的事实：

    - (a)：
      思考：
      为什么是这个答案：
    - (b)：
      思考：

    - (c)：
      思考：
      为什么是这个答案：

- 词：

过程状态只有正在对齐、对齐完毕。重述的状态只有未确认、已确认、已否定。询问的状态只有未确认、已确认、已否定。术语的状态只有未确认、已确认。改正不覆盖已写下的轮次或题目。

## 术语文件

已确认的词写入仓库根目录的 `CONTEXT.md`。已有 `CONTEXT-MAP.md` 时，写入它指向的那份 `CONTEXT.md`。文件不存在就在第一个词确认时创建。这里不写需求 UUID、对齐 UUID 或会话 UUID。

`CONTEXT.md` 只放术语。定义写它是什么，一两句。不写它做什么，不写实现，不写重述过程，不写询问。

```markdown
# <这一语境的名称>

<这一语境是什么，一两句。>

## Language

**<词>**:
<它是什么。>
_Avoid_: <放弃的叫法；没有则省略这一行>
```

## 结论文件

`.scratch/需求工程/<需求名称>/对齐/<对齐名称>/结论.md`

这是临时文件，和过程文件放在一起，整体任务结束后随该需求的临时目录删除。调用方写需求简述时只取「原话结论」。

```markdown
# 对齐结论

对齐 UUID：<与过程文件相同。>
需求 UUID：<与过程文件相同。>
会话 UUID：<与过程文件相同。>

## 原话

<与过程文件相同。>

## 原话结论

<最后一轮已确认的重述。>

## 已确认的询问

- 问题：<问句>
  选择：<已确认的选择。对方自己给出的答案照实写。>
```

没有已确认的询问时，这一节写「无」。

此后若再改正，把过程状态改回「正在对齐」。重述有改正，就追加一轮重述。询问有改正，就追加一题，并写明改正的是哪一题。新的已确认重述替换「原话结论」。被改正的询问在「已确认的询问」里换成新题的选择。按确认结果改 `CONTEXT.md`，再把过程状态改回「对齐完毕」。原话不改。

## 不做

- 不把未确认的重述或未确认的询问写入 `结论.md` 或地图。
- 不把各次对齐集中写进 `.scratch/需求工程/对齐/`。
- 不把需求 UUID、对齐 UUID 或会话 UUID 放进路径。
- 不开始初始调研，不划边界，不建票。
- 不查竞品怎样做，也不查没有这类产品时工作怎样开展。
- 不问第一版做到哪一档，不问界面如何放置，不问实现。
- 不问不会改写这句原话含义的今后决定。
- 不一次问出多题。
- 不把探索到的事实拿去问对方。
- 不用需求名称或对齐名称判断两条原话是不是同一条需求。
- 不用需求 UUID 或会话 UUID 代替对齐 UUID。
