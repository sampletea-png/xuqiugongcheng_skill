# 调研任务怎样完成

本技能调研同一件工作怎样完成。一份是未使用竞品，一份是使用竞品。两边结构相同。竞品可以有多个，找到几个就写几个，不合并。

做法放在这一个技能里。有的做法相近，有的互相补充，有的只在某类材料存在时用。不拆成多个技能。

需求目录是 `.scratch/需求工程/<需求名称>/`。其中必须已有 `需求.md` 和 `简述.md`。没有需求名称、需求 UUID 或简述时停下。不另起名称，不另生成需求 UUID。

## 步骤

1. 从 `需求.md` 读取需求 UUID，从 `简述.md` 读取这件工作。调研只沿这件工作。
2. 按手头材料选用做法，写入两份文件。某一节没有材料就写「材料里没有」，不留空，也不补造。没有出处的内容不写。
3. 此时还不决定软件怎样做。

未使用竞品时：

- 已有稿纸、表格、文档、邮件或清单，就做工件分析。
- 简述或工件里能指出任务，就做任务分析。只拆有出处的任务。
- 任务或工件已经能看出先后，就走查现状流程，并写出这段做法的边界，以及哪里没接住。

使用竞品时，每个产品都按这个顺序：

- 找出正在承担这件工作的产品。可以有多个。
- 先使用该产品，或读它自己的文档，把已经看到的全部功能写入 `初始-竞品功能.md`。每一条结构相同，状态先写未分析。看到的不遗漏，没看到的不编造。
- 再根据这些功能整理任务、工件、流程、边界和没接住，写入 `初始-竞品.md`。开始整理某一条时，把它的状态改为正在分析。整理完并在 `初始-竞品.md` 里指回该功能后，改为已分析。指不回功能的不写。状态只有未分析、正在分析、已分析。
- 没接住写缺陷、旁边另用的工具，或不如未使用竞品的做法方便。

不到现场做情境询问、跟随观察、现场访谈或工作坊。

## 文件

`.scratch/需求工程/<需求名称>/初始-原始流程.md`

```markdown
# 未使用竞品完成这件工作

需求 UUID：<与需求.md 相同。>

## 任务

- 任务 · 来源
  谁做。输入是什么。产出是什么。

## 工件

- 工件 · 来源
  它在这段工作里的位置。上面有哪些项。缺了会怎样。

## 流程

- 顺序 · 来源
  从哪里开始，到哪里结束。实际做法。交给下一手的是什么。

## 边界

<这段做法接住这件工作的哪一段。>

## 没接住

<哪里没被这段做法接住。>
```

`.scratch/需求工程/<需求名称>/初始-竞品功能.md`

```markdown
# 竞品功能

需求 UUID：<与需求.md 相同。>

- 功能：<名称>
  产品：<竞品名称>
  来源：<亲自使用，或该产品自己的文档。>
  状态：未分析
```

每一条都写这四行。状态只写未分析、正在分析、已分析，不省略。有几个产品，功能就按产品分别列出，条目结构不变。

`.scratch/需求工程/<需求名称>/初始-竞品.md`

```markdown
# 使用竞品完成这件工作

需求 UUID：<与需求.md 相同。>

## 产品：<名称>

来源：<亲自使用，或该产品自己的文档。>

### 任务

- 任务 · 来源
  谁做。输入是什么。产出是什么。

### 工件

- 工件 · 来源
  它在这段工作里的位置。上面有哪些项。缺了会怎样。

### 流程

- 顺序 · 来源
  从哪里开始，到哪里结束。实际做法。交给下一手的是什么。

### 边界

<它接住这件工作的哪一段。>

### 没接住

<缺陷、旁边另用的工具，或不如未使用竞品的做法方便。>

## 产品：<另一个名称>

<功能仍写在初始-竞品功能.md。这里再写一套相同的任务、工件、流程、边界、没接住。>
```

没有找到这类产品时，`初始-竞品.md` 只写：没有找到正在承担这件工作的产品。并写明查找来源。

`初始-竞品功能.md` 是竞品调研的起点，不是要做的需求。任务、工件、流程、边界和没接住从状态变为已分析的功能整理出来，只作参考。

## 不做

- 不写 `粗边界.md`，不写 `map.md`，不建票。
- 不研究图形如何展示、数据如何交互。
- 不把竞品功能清单直接写成需求。先列出功能，再从功能整理流程和边界。
- 不把竞品的边界写成这件工作的粗边界。
- 不分辨任务是否为用户所期望，不决定哪一条优先。
- 不调用其他技能。
