# 初始调研与粗边界

本技能只服务已经在处理的这一件工作。先写两份材料，再从工作流提出软件辅助的哪一段，请人确认。确认之前不把提议当作粗边界。

需求目录是 `.scratch/需求工程/<需求名称>/`。其中必须已有 `需求.md` 和 `简述.md`。没有需求名称、需求 UUID 或简述时停下。本技能不另起名称，也不另生成需求 UUID。

## 步骤

1. 从 `需求.md` 读取需求 UUID 和需求名称，从 `简述.md` 读取这件工作。调研只沿这件工作。
2. 使用 `research-task-completion` 写下两份材料。本技能不代替它调研。此时还不决定软件怎样做。
3. 从 `初始-原始流程.md` 的任务、流程和边界提出粗边界：软件辅助这件工作的哪一段。工件用来核对人们已经依赖的做法。对照 `初始-竞品.md` 里每一个产品的任务、工件、流程和边界。未使用竞品只有一份。使用竞品时，每个产品各有一份相同结构。竞品材料是参考，不把某一个竞品的边界直接写成提议。写入 `粗边界.md`，状态为未确认，然后把提议交给人。
4. 人确认、改正或否定。改正或否定就改提议再问。某一份提议被确认后，把确认写上，状态改为已确认。未确认时停下，不交给调用方去写地图。

过程中若看到与当前需求无关、或当前不便处理的事项，写进材料，并在提议里单独列出，交回 `open-rough-map`。本技能不调用 `capture-uncharted`，不判断哪一条优先。

## 材料

两份调研产物的结构相同。未使用竞品只有一份。使用竞品时可以有多个产品，每个产品各写一套相同的五节。

- `.scratch/需求工程/<需求名称>/初始-原始流程.md`
- `.scratch/需求工程/<需求名称>/初始-竞品功能.md`
- `.scratch/需求工程/<需求名称>/初始-竞品.md`

```markdown
# <未使用竞品完成这件工作，或使用竞品完成这件工作>

需求 UUID：<与需求.md 相同。>

## 任务

- 任务 · 来源
  谁做。输入是什么。产出是什么。

## 工件

- 工件 · 来源
  它在这段工作里的位置。上面有哪些项。缺了会怎样。

## 流程

- 顺序 · 来源
  从哪里开始，到哪里结束。实际做法。交给下一手的是什么。

## 边界

<这段做法接住这件工作的哪一段。材料里没有则写「材料里没有」。>

## 没接住

<哪里没被这段做法接住。材料里没有则写「材料里没有」。>
```

`初始-竞品.md` 按产品重复这一套，有几个产品就写几节，不合并。每个产品先写名称和来源，下面仍是任务、工件、流程、边界、没接住。没接住在竞品下面写缺陷、旁边另用的工具，或不如未使用竞品的做法方便。这些是参考，不写成要做的功能。

某一节没有材料时写「材料里没有」，不留空，也不补造。

## 粗边界

`.scratch/需求工程/<需求名称>/粗边界.md`

```markdown
# 粗边界

需求 UUID：<与需求.md 相同。>
状态：未确认

## 提议

<从工作流提出的一段：软件辅助这件工作的哪一段。不写精细交互。>

## 这一步说不细

<仍属于这件工作、但这一步说不细的事项。没有则空着。>

## 交回开图

<与当前需求无关，或当前不便处理的事项。没有则空着。>

## 确认

<人确认后的粗边界。未确认时空着。>
```

人确认之后，状态改为已确认，确认一节写上人接受的那段。人明确放到这件工作之外的，写在确认一节里，并注明是人明确放下的。没表态的能力不写成范围之外。

## 不做

- 不写 `map.md`，不建票，不写规格。
- 不研究图形如何展示、数据如何交互。
- 不把竞品有的功能直接写成需求。
- 不分辨任务是否为用户所期望，不决定哪一条优先。
- 不调用 `research-task-completion` 以外的技能。
- 不使用情境询问、跟随观察、现场访谈或工作坊。
